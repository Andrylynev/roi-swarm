# ROI Swarm — коллективный разум

Рой ИИ-агентов на LangGraph, который подключается к любому клиенту OpenAI API (в том числе к Hermes Agent) как одна модель `roi-swarm`:

- **центральная модель** (по умолчанию `claude-opus-5-5`) оценивает задачу, планирует и собирает итог;
- задачи, которые делятся на ≤3 части, она решает сама; больше — делит на атомарные подзадачи, и их **параллельно** решают воркеры (по умолчанию `gpt-6-luna`) — без лимита параллельности;
- программный verifier и критик проверяют результаты; 3D-дашборд показывает работу роя вживую;
- режим сна включён по умолчанию: рой анализирует завершённые запуски во время простоя; автоприменение правок кода включается отдельно (только после тестов и независимого ревью).

Все модели облачные, через ваш OpenAI-совместимый провайдер. Локальные модели не нужны.

## Установка одной командой

На сервере Linux с systemd (основная цель — Ubuntu/Debian; другие дистрибутивы и macOS — без гарантии автоматического сервиса):

```bash
curl -fsSL https://raw.githubusercontent.com/Andrylynev/roi-swarm/main/install.sh | bash
```

Установщик:

1. ставит `git`/`curl` при необходимости, [uv](https://docs.astral.sh/uv/) и Python 3.11;
2. клонирует рой в `/opt/roi-swarm` (root) или `~/.roi-swarm`;
3. спрашивает **URL и API-ключ провайдера** (ключ вводится скрыто), проверяет их запросом `GET /models`, показывает доступные модели и предлагает выбрать центральную модель и модель воркеров;
4. генерирует токен доступа `ROI_SWARM_API_KEY` и пишет всё в `.env` (`chmod 600`);
5. при наличии systemd регистрирует сервис systemd `roi-swarm` (автозапуск, перезапуск при сбое; от root — под отдельным пользователем `roi-swarm`) и проверяет, что сервер отвечает;
6. печатает адрес дашборда, токен и блок настроек для Hermes.

Без вопросов (cloud-init, Ansible, CI):

```bash
curl -fsSL https://raw.githubusercontent.com/Andrylynev/roi-swarm/main/install.sh | \
  ROI_PROVIDER_BASE_URL=https://provider.example/v1 ROI_PROVIDER_API_KEY=sk-... \
  bash -s -- --non-interactive --host 0.0.0.0 \
    --main-model claude-opus-5-5 --worker-model gpt-6-luna
```

| Флаг | Переменная | Назначение |
|---|---|---|
| `--provider-url` | `ROI_PROVIDER_BASE_URL` | OpenAI-совместимый endpoint (`…/v1`) |
| `--provider-key` | `ROI_PROVIDER_API_KEY` | ключ провайдера |
| `--main-model` / `--worker-model` | `ROI_MAIN_MODEL` / `ROI_WORKER_MODEL` | модели центра и воркеров |
| `--host` / `--port` | `ROI_HOST` / `ROI_PORT` | `0.0.0.0` — доступ из сети (только с токеном), `127.0.0.1` — локально; порт 8765 |
| `--api-key` | `ROI_SWARM_API_KEY` | свой токен доступа вместо сгенерированного |
| `--dir` / `--branch` | `ROI_INSTALL_DIR` / `ROI_BRANCH` | каталог и ветка |
| `--reconfigure` | | заново спросить провайдера и модели |
| `--no-service` | | без systemd |
| `--uninstall` | | удалить сервис и установку |

**Обновление** — та же команда: код обновится только fast-forward, `.env` и индивидуальный выбор моделей сохранятся. Если есть локальные правки или коммиты самоулучшения, установщик их не сбрасывает и сообщает о пропуске обновления. **Смена провайдера** — `… | bash -s -- --reconfigure`. **Удаление** — `… | bash -s -- --uninstall`.

Windows: используйте WSL2 (Ubuntu) и ту же команду.

### Безопасность

- Секреты есть только в `.env` на сервере клиента; в репозитории их нет (`.env`, `data/`, `runs/` в `.gitignore`).
- `/v1/*`, `/api/*` и данные дашборда требуют `Authorization: Bearer <ROI_SWARM_API_KEY>`. Сервер **отказывается** слушать сеть (`ROI_HOST` не loopback) без токена.
- Трафик — HTTP. Для доступа через интернет поставьте перед роем HTTPS-прокси (Caddy/nginx) или используйте VPN/SSH-туннель.
- Воркеры-агенты Hermes и режим сна исполняют код с правами сервиса — это не песочница. Поэтому сервис работает под отдельным пользователем. Сон включён по умолчанию и расходует запросы провайдера; автоприменение изменений кода выключено.

## Подключение к Hermes

Добавьте провайдера через `hermes model` → Custom endpoint (URL роя, его токен, модель `roi-swarm`). Эквивалентная структура в `~/.hermes/config.yaml`:

```yaml
providers:
  roi-swarm:
    name: ROI Swarm
    base_url: http://<сервер>:8765/v1
    key_env: ROI_SWARM_API_KEY
    api_mode: chat_completions
    default_model: roi-swarm
    models:
      roi-swarm:
        context_length: 1000000
```

в `~/.hermes/.env` — `ROI_SWARM_API_KEY=<токен из установщика>`, затем:

```bash
hermes chat --provider roi-swarm -m roi-swarm
```

Любой другой клиент OpenAI API: `base_url=http://<сервер>:8765/v1`, `api_key=<токен>`, `model=roi-swarm`.

Если на том же сервере установлен Hermes (`~/.hermes/hermes-agent`), рой включает волновой режим: каждая подзадача выполняется полноценным агентом Hermes с инструментами в отдельном git worktree. Без Hermes рой работает через координатор.

## Управление

```bash
sudo systemctl status roi-swarm      # или: systemctl --user status roi-swarm
sudo journalctl -u roi-swarm -f
sudo -u roi-swarm /opt/roi-swarm/.venv/bin/roi-swarm models
sudo -u roi-swarm /opt/roi-swarm/.venv/bin/roi-swarm run "задача"
```

Дашборд: `http://<сервер>:8765/dashboard#token=<токен>` (токен сохраняется в браузере; URL fragment не отправляется серверу и не попадает в access log). Модели по ролям меняются на дашборде («Модели по ролям») без перезапуска; выбор хранится в `data/model-settings.json`.

## Установка зависимостей в волнах Hermes

Волновые воркеры получают отдельные Git worktree, но `.venv` и `node_modules` подключены
из основной папки. Поэтому устанавливает пакеты **центральный брокер**, а не воркер:

- Отдельная foreground-команда `uv pip install ...`, `pip install ...`, `npm ci` и т. п.
  выполняется в основной папке проекта. Абсолютные пути worktree переводятся обратно.
- Один брокер обслуживает все одновременные запросы сервиса: установки последовательны,
  он ждёт окончания активных инструментов и не пускает новые до освобождения очереди.
  Ожидание видно в потоке; таймаут ожидания не вводится.
- Фоновые команды сохраняют блокировку до фактического завершения процесса. Перед
  завершением воркера закрывается приём новых инструментов, завершаются уже начатые
  вызовы и останавливаются оставшиеся процессы. Родитель дополнительно владеет деревом
  процессов ОС (Windows Job Object): даже после выхода host его потомки завершаются
  **до снятия блокировки**. Неподтверждённая очистка блокирует дальнейшие установки.
- Нельзя смешивать установку с `cd`, тестами или другими командами через `&&`, pipe и т. п.
  Укажите каталог через `workdir`; установку из `execute_code` повторите отдельным вызовом
  терминала. Это предотвращает выполнение правок и тестов в основной папке в обход merge.
- `uv run` может неявно синхронизировать окружение: для тестов в worktree используйте
  `uv run --no-sync ...`. Пересоздание общей `.venv` во время работы не допускается.
- Python-установка требует существующую проектную `.venv`. Если в ней нет `pip`, fallback
  в Hermes/global запрещён: используйте `uv pip install --python <проектная .venv/python> ...`.
  Явные внешние интерпретаторы и глобальные/целевые переопределения отклоняются.
  `conda`/`mamba` пока не поддерживаются: они не используют проектную `.venv`.
  Для npm принудительно задаётся локальная цель, независимо от унаследованных настроек.
- До/после волн проверяются хеши `.pth`, editable `direct_url.json` и
  `node_modules/.package-lock.json`. Изменение в обход брокера или ссылка на удаляемый
  worktree останавливает следующие волны до восстановления окружения. Автоматической
  переустановки неизвестного состояния нет.

Это координация и обнаружение ошибок, **не OS sandbox**: произвольный скрипт или внешний
процесс с теми же правами может обойти проверку команд. Проверка метаданных также не
обнаруживает любую возможную правку файлов пакетов.

Проверка реального Hermes dispatch и editable-установки без LLM/сети, в удаляемом проекте:

```bash
uv run python scripts/probe_install_broker.py
```

Live-граф работы роя доступен по адресу:

```text
http://127.0.0.1:8765/dashboard
```

Он показывает живую 3D-визуализацию роя (Canvas, без библиотек, ~30 fps, пауза в фоновой вкладке), режим (Opus напрямую или рой), этапы конвейера, оценку задачи, карточки подзадач, ответ, ленту событий и общую статистику. История запусков хранится в `runs/`.

## Локальный контекст и RAG

ROI Swarm обрабатывает всю историю OpenAI messages, включая system, assistant tool calls и tool results. Контекст проходит через:

```text
normalization → canonical state → artifact spill → SHA-256 dedup → role packs → hybrid RAG
```

Крупные оригиналы сохраняются в `data/context/artifacts`, snapshots/deltas — в `data/state`, а индекс — в `data/rag/rag.sqlite`.

По умолчанию поиск лексический (BM25) — без локальных моделей. Векторный поиск (опция) выполняет CPU-модель `ibm-granite/granite-embedding-97m-multilingual-r2` (ONNX FP32, кэш в `data/models/huggingface`):

```bash
uv sync --extra embeddings --extra dev
echo ROI_RAG_EMBEDDINGS=true >> .env
```

Индексация каталога (`--embeddings` — с векторами):

```bash
uv run roi-swarm-rag /srv/docs --collection myproject_docs
```

и привязка коллекции к проекту в `config/settings.yaml`: `rag.project_collections: {myproject: [myproject_docs]}`.

Для каждого worker формируется отдельный context pack. Метрики входного и упакованного контекста, артефактов, dedup и RAG-фрагментов отображаются в дашборде.

### Полные материалы и изоляция проектов

Планировщик получает оригиналы сообщений и результатов инструментов, включая середину больших файлов и ранее вынесенные артефакты. Точные дубликаты передаются один раз. Бюджет окна `context.worker_context_tokens: 800000` применяется к каждому воркеру, роутеру и критику; `context.main_context_tokens: 1000000` — к планировщику, синтезатору, прямому ответу и координатору Hermes. В бюджет входят системные инструкции, JSON-схемы/инструменты и резерв `max_output_tokens` под ответ. Пределы длины ответа отдельно не увеличены.

Планировщик назначает крупные оригиналы короткими маркерами `[[message:N]]` (нулевой индекс из `ORIGINAL CONVERSATION`). Перед вызовом воркера код раскрывает маркер в полный неизменённый текст. Поэтому предел длины ответа планировщика не заставляет его перепечатывать сотни тысяч токенов. Неразрешимая ссылка явно проваливает подзадачу, а неназначенные большие материалы не подмешиваются всем воркерам.

Старые ограничения `maximum_pack_chars: 12000` и `planner_input_limit_chars: 500000` отключены (`null`). По умолчанию назначенные материалы и выбранные релевантные фрагменты передаются без прежней обрезки по символам. Это доступный бюджет, а не заполнение окна пустым текстом и не копирование всей задачи каждому воркеру. При превышении токенного бюджета — явная ошибка, без молчаливой потери исходников.

Подсчёт выполняется локальным reference tokenizer `o200k_base` (`context.token_encoding`), а не формулой «символы / 4». У моделей за псевдонимами прокси нативный tokenizer может отличаться. Пользователь отвечает за поддержку выбранными моделями заявленного окна; проверка реального миллионного запроса не выполняется автоматически.

RAG не выбирает проект по словам, пути из промпта или текущему каталогу сервера. В `/api/run` и `/v1/chat/completions` можно передать `project_id`, например `"myproject"`. Разрешённые коллекции задаёт оператор в `rag.project_collections`, например `myproject: [myproject_docs]`. Без `project_id` либо без соответствующего mapping поиск отключён; старый `rag.collections` не открывает общую базу. В обычных запросах Hermes без поля `project_id` проектный RAG отключён, а переданные файлы по-прежнему доступны. Это разделение контекста, не многопользовательская авторизация.

### Отдельная память опыта роя

`data/experience/experience.sqlite` — отдельная SQLite-база (WAL), не индекс исходников RAG и не дообучение весов. Воркеры могут возвращать до двух `workflow_lessons`: область (`decomposition`, `materials`, `verification`, `coordination`), ситуация, рекомендация и наблюдение. Runner сохраняет их как `candidate`, с ID запуска, проектом, временем и учётом повторов; автоматически также сохраняются числовые метрики работы. Уверенность модели и статус verifier не превращают заметку в доказанный факт.

Только `approved`-заметки включаются в следующие планы как ограниченный набор необязательных советов, не как инструкции или доказательства. По умолчанию заметки строго проектные; для запросов без проекта используется изолированная область `run:<id>`. Универсальный совет можно явно опубликовать в `global`, но только операторским действием. Секретоподобные значения отклоняются, автоматические заметки с путями исходников не сохраняются. Это защитные фильтры, а не гарантия удаления любой конфиденциальной информации: перед общим использованием заметку нужно проверить.

API (с той же авторизацией, что у остальных API):
- `GET /api/experience?project_id=myproject&status=candidate` — список заметок;
- `POST /api/experience` — операторская заметка: поля `project_id`, `run_id`, `lesson`;
- `PATCH /api/experience/1` с `{"status":"approved"}` или `{"status":"rejected"}` — проверка;
- `PATCH /api/experience/1` с `{"status":"approved","publish_global":true}` — явное распространение универсального совета.

Область `global` зарезервирована: обычные запуски с таким `project_id` отклоняются; модель не может записывать туда кандидатов. Глобальная публикация выполняется одной транзакцией и возвращает опубликованную операторскую запись. Некорректные необязательные lessons отбрасываются отдельно от полезного ответа воркера. Сбой базы опыта не останавливает основной расчёт: используются пустые lessons, в телеметрии фиксируется ошибка, API памяти возвращает безопасный 503. Метрики различают число запланированных задач, реально полученные результаты и повторные попытки.

Общие заметки также можно отозвать, указав их собственный ID из `GET /api/experience?project_id=global`. Отзыв исходной проектной заметки не отзывает отдельную опубликованную копию. Управление памятью пока доступно через API, отдельной панели на дашборде нет. Чтобы отключить накопление/использование опыта, установите `experience.enabled: false`. Рост качества не гарантирован: его нужно оценивать по одинаковым контрольным задачам до и после подтверждения уроков.

## Режим сна (самоулучшение)

После завершения задачи фоновый Critic исследует эффективность работы роя. В новой клиентской установке сон **включён по умолчанию**. Он запускает фоновое исследование после завершённой задачи во время простоя, а не делает вызовы без исходного запуска. Отключение — переключателем на дашборде или `ROI_SLEEP_ENABLED=false` в `.env` до первого старта. Сохранённый выбор переключателя имеет приоритет после перезапуска; обновление не перезаписывает существующее отключение в `.env` или checkpoint. Лимитов нет: `max_steps_per_cycle: null`, `daily_call_limit: null`. Между шагами — пауза 30 секунд, запуск после 15 секунд простоя. Это **реальные вызовы внешнего провайдера**, которые могут расходовать деньги без суточного потолка. Остановить их можно переключателем «Режим сна» на дашборде или `PUT /api/sleep` с `{"enabled":false}`; выбор сохраняется после перезапуска.

Публичный checkpoint хранится в `data/experience/sleep.sqlite` (SQLite WAL): числовые метрики исходного запуска, наблюдения, гипотезы, проведённые проверки, следующий шаг и счётчики. Это не сохранение скрытой цепочки рассуждений или возобновление с оборванного токена. Новый запрос отменяет фоновый вызов, сохраняет checkpoint и получает приоритет; поздний результат отменённого шага не должен попадать в память или автоприменение. После выполнения задачи исследование продолжается, в том числе после перезапуска сервера.

Между выдачей инструментов Hermes и возвратом их результатов сон остаётся на паузе: активные tool-call ID сохраняются отдельно в `data/experience/tool-leases.json`. Если Hermes закрыли во время инструмента, оператор может снять оставшееся ожидание кнопкой на дашборде или `POST /api/sleep/release-tools` **только убедившись, что внешние инструменты остановлены**. Неизвестное состояние или ошибка хранения не должны считаться безопасным простоем.

`ROI_SLEEP_AUTO_IMPROVE=true` разрешает небольшие Git-улучшения: предложение → отдельный worktree `<каталог>-worktrees` → полные pytest и Ruff → отдельный вызов Critic для независимой рецензии → один коммит → fast-forward. Модель не может задавать команды проверок, ослаблять старые тесты или менять модули авторизации/самоконтроля. Чужие незакоммиченные изменения не коммитятся, не stash/reset и не перезаписываются: **грязный основной репозиторий блокирует автоприменение**, но не обычную рефлексию. Это рабочая копия для проверки, **не OS-песочница**: Python-тесты исполняются с правами процесса сервера. Для обработки враждебных предложений требуется отдельная учётная запись/изоляция ОС.

Продвижение кода не означает горячую перезагрузку уже импортированных Python-модулей: API показывает `restart_required`, повторные изменения блокируются до перезапуска сервиса. `/api/sleep` показывает фактические счётчики и блокировки, `/api/sleep/snapshot` — публичный снимок. Увеличение качества не гарантировано без сравнения на контрольных задачах.

## Замена моделей

Модели по умолчанию — в `config/settings.yaml`; выбор установщика и дашборда (`data/model-settings.json`) имеет приоритет:

```yaml
models:
  router:
    model: gpt-6-luna
  planner:
    model: claude-opus-5-5
  worker:
    model: gpt-6-luna
  synthesizer:
    model: claude-opus-5-5
```

`provider.api_mode: chat_completions` подходит большинству прокси; `responses` — для провайдеров с OpenAI Responses API. `provider.timeout_seconds: null` отключает таймаут запроса к провайдеру.

Для смены OpenAI-compatible провайдера измените `ROI_PROVIDER_BASE_URL` и `ROI_PROVIDER_API_KEY` в `.env` (или `install.sh --reconfigure`) и перезапустите сервис.
